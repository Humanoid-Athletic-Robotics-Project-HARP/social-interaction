`submission/` is our code on top of him-sim2real-management ([[him-sim2real]]): one image, `harp-submission:local` (`build.sh`), plus a thin layer per world (`harp-submission:NAME`, `Dockerfile.world`); a git worktree has its own image names ([[worktrees]]).

**How it fits:** `build.sh` runs HIM's own `containers/examples/prepare.py walker` into `submission/.build/` (ignored) and builds on it, so the walker, its client and its joint profile are HIM's, unchanged. `harp_node.py` subclasses HIM's `client.PolicyNode`: the task velocity is the latest `/cmd_vel` (clipped to 0.6/0.4 m/s, 1 rad/s; zero after 0.5 s), and each state is republished by `harp/state.py` (`/odom`, `/tf`, `/joint_states`, `/imu`). Leg odometry runs on HIM's G1 model (`/harp/model`, MuJoCo 3.2.3, the newest for Python 3.8). The lidar mount is the rev 1.0 URDF's.

**Waypoint capture:** the read-only recorder and host launcher share the running image's ROS network; export and session limits are in [[waypoint-recorder]].

**Size:** `submission.tar` is about 306 MB (gzip layers; 970 MB as one stage). HIM sets no limit; its walker example is 277 MB and `ros:foxy-ros-base` alone 252 MB, so there is little left to cut. The `Dockerfile` has two stages: `build` compiles (CycloneDDS, HIM's interfaces, our Graceful port) and pip-installs, and the image copies in only the results. Foxy's debs name far more than they load: STVL names all of PCL (its visualization brings VTK and Mesa's GL drivers), `behaviortree_cpp_v3` names `libboost-all-dev` (OpenMPI, then apt picks the Flang compiler, 950 MB), `pcl_conversions` is headers only. The image installs empty stand-in debs under those names, so apt stays consistent and only the libraries STVL and Nav2 load (about 170 MB) come in. It also uninstalls OpenCV, SymPy and PyOpenGL (pulled in by Unitree's SDK, ONNX Runtime and MuJoCo, never imported). If a new package fails to load a library, `ldd` its `.so` in the image and add the real runtime package, not the stand-in's name. All six courses ran on it (`runs/*_two-stage`, 2026-10-28), like the one-stage image.

**Worlds** (`submission/worlds/`, criteria in `NAME.yaml`): `stage_world.py` writes HIM's scene (the G1, `safety_floor`, fixed obstacles; movers left out, or HIM would hold them still where they start) and the image's copy with movers. Worlds must be includable next to HIM's G1: defaults go in a named class (`obstacle`), never the top-level default. The comments' "--" breaks XML parsers, so `stage_world.py` strips comments.

**In a world's image** (`entrypoint.sh`): `harp/lidar.py`, Nav2 (`nav2/`), `harp/approach_stop.py` (passes Nav2's `/cmd_vel_nav` on to `/cmd_vel`, or zero while something comes at the robot: [[nav2-sim]]) and `harp/course_goal.py`, each its own process, beside `harp_node.py`, unless a `{"to": ...}` target is given: only one thing drives `/cmd_vel`. They start first, and `harp_node.py` only once Nav2 is configured (`harp/nav2_ready.py`, at most 15 s), so their start-up is over before HIM times our commands ([[sim-deadline-stops]]).
- The lidar must stay out of the policy's process: publishing its 190 KB cloud there made the node miss HIM's 0.2 s deadline (`action_timeout`, HIM's Holosoma caught the robot).
- HIM's sim Fast DDS profile finds only participants 0-4; with Nav2 we run about ten, and Nav2's bringup hung. `harp/fastdds_profile.py` lists peers for 32 on the same localhost transport, only when HIM's `/fastdds.xml` is set.
- Foxy Nav2 (0.4.7): `recoveries_server`, `plugin_lib_names` must be listed (the default names a library Foxy doesn't ship), `server_timeout="200"` on each BT action node. Foxy has no Graceful Controller, so `submission/nav2_graceful_controller/` is our port of it (built by the Dockerfile; changes in its `HARP_PATCHES.md`). Settings and results: [[nav2-sim]].

**Course tests:** `python3 submission/course.py NAME [--tag T --repeat N --view]` runs `sim.sh --world` into the main checkout's `runs/` (shared by every worktree, [[worktrees]]) and scores from HIM's `trace.npz` (truth) and `policy.log` (our events and "odom" lines): outcome, pass, time, path, end error, closest, contacts (movers included), recoveries, drift. Container output is only in `policy.log`; nothing else leaves the container. `run.json` records the git commit and branch and whether the tree was dirty (the diff in `git.diff`); `--compare [WORLD]` lists runs by world and tag. Builds and runs wait for each other, one at a time per computer (the sim lock, [[worktrees]]).
- **Run folders and pruning:** `sim.sh --output DIR` (so every course run) writes `run.json` (made there for a plain `sim.sh` run) with `"sim"`: its arguments, image and image id, `G1_TASK_COMMAND`, HIM's full commit; and the scene HIM loaded minus HIM's G1, in `scene/` (HIM's flat `scene.xml` without `--scene`). Without `--output` the run goes to HIM's own output folder and is left alone. After each run (`sim.sh` once HIM's viewer is closed, `course.py` after scoring and the `--view` replay), and with `course.py --prune [RUN]`: HIM's viewer output goes, and every `trace.npz` but the newest 2 of each world (plain `sim.sh` runs are one group; per tag kept 60 of 69) loses `model` (the compiled scene, 47 MB) and `thrash` (5 MB). It strips only when the scene rebuilt from `scene/` and HIM's G1 at that commit (`git archive`, read-only) matches the trace's (joints, bodies, geom names, types, sizes and poses, mesh vertices); scoring needs only `time` and `qpos`. Runs from before `"sim"` existed got theirs filled in only where the rebuild matched (all 68 on 2026-10-28; `"backfilled": true`). `runs/` went from 3.0 GB to 0.8 GB. `course.py --replay RUN` serves HIM's replay from a copy of the trace with the scene put back (the thrash panel is empty once stripped). Whole runs are never deleted: that's a separate decision. A run goes on for the world's `max_time_s` plus 12 s (`STARTUP`; Nav2 sends the goal about 6 s in) whatever happens, so after the goal GR00T stands, its heading creeping about 0.1°/s.
- **Routes** (`--route NAME_OR_FILE` from `submission/routes/`, or `--waypoint X Y [HEADING]` per point, `--laps N`; format in `harp/route.py`): `course.py` validates the route, saves it as the run's `route.yaml` and passes it as `G1_TASK_COMMAND` `{"route": ...}` to `course_goal`, which visits each point in turn and moves on only after Nav2 reports it reached; a rejection, failure or timeout (240 s per point, finding Nav2 and acceptance included) ends the route. Scoring then uses the route's last point for the end error and its own `criteria` (none: no verdict). HIM's run length is fixed, so `course.py` sizes it from the route's `max_time_s`, or 0.15 m/s along its legs plus 10 s per point. `course.py` exits 1 if any run didn't succeed or failed its criteria. `rectangle` on `one_box`, one lap: 4/4 points, 73.6 s, closest 0.59 m, 0 contacts or recoveries (`runs/2026-10-28_09-30-12Z_sim_one_box_route`).

**Planned moves** (`harp/moves.py`): `G1_TASK_COMMAND` with `"moves"` or `"to"` reaches our image both in HIM's sim and through its robot launcher, and HIM's client is told it isn't a velocity ([[planned-moves]]). With `G1_TASK_COMMAND` empty and no world in the image, `entrypoint.sh` uses the image's `HARP_DEFAULT_TASK` (`Dockerfile`), so operators who launch it without a task still get the move; HIM passes the variable empty when unset, so an image `ENV` of `G1_TASK_COMMAND` itself would be overwritten. A world image keeps Nav2 and its course goal.

**Run length:** a `sim.sh` run always lasts HIM's 5 s start-up balance plus `--seconds` plus 5 s of Holosoma balance after our container is stopped (`G1_SIM_HANDOFF_SECONDS`), whether or not the moves are done: our image never exits on its own. Holosoma's takeover can shift the standing robot a few cm (4 cm in the (0.5, 0.5) run), so score a move at its `move_done`, not at the trace's end. Docker start-up and the report add wall time, and HIM's viewer stays up until Ctrl-C.

**Viewing:** `submission/sim.sh` opens HIM's live browser viewer by default (press Start; `--no-view` to skip). `course.py --view` runs each course in HIM's live viewer: it prints the URL and waits for Start on the page (HIM's page fetches frames only after its own Start; pressed mid-run it plays from the first frame, the sim isn't restarted), POSTing `/start` itself after `START_WAIT` (120 s, an unseen run); it Ctrl-Cs `sim.sh`'s session 10 s after HIM's report (`VIEW_LINGER`), so one viewer is up at a time, and puts the report back if Start on the finished page deleted it (HIM's `/start` unlinks it); `sim.sh` then prunes. Before each run it warns about HIM viewers still up (`live.py`, about 700 MB each) and macOS memory pressure; `run.json` gets `host_memory` (macOS `vm_stat`: least free, most compressed, MB decompressed in all and in the worst second; Linux: available and swapped in). Why: [[sim-deadline-stops]]. HIM's first viewer use downloads Three.js; on a Python.org Python that needs `SSL_CERT_FILE` from `certifi`.

**Lidar relay** (`harp/lidar_relay.py`, robot only: `entrypoint.sh` starts it when `G1_EXECUTION_MODE` isn't `sim`): reads `rt/utlidar/cloud_livox_mid360` through Unitree's SDK on `ROBOT_DOMAIN`/`ROBOT_INTERFACE` (HIM's launcher sets them) and republishes it restamped for Nav2. The SDK needs CycloneDDS 0.10.2's C library, built from source in the Dockerfile (no wheel for Python 3.8 on ARM64); it sits beside ROS's Fast DDS in one process without trouble. Tested in the image (2026-10-28) against a cloud published the way the robot does: 15,000 points arrive restamped; SIGTERM exits cleanly. Foxy's `rclpy.spin` never wakes for signals, so it spins in 0.2 s steps. In a plain `docker run`, `lo` has no multicast, so ROS discovery needs `harp/fastdds_profile.py`'s profile; on the robot HIM uses host networking. Real lidar data needs the robot.
