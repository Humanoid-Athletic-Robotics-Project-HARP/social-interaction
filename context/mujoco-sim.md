**What we use:** `ros2/src/harp_sim/harp_sim/run_sim.py`, run with `ros2 run harp_sim run_sim` after `pixi shell --as-is` in `ros2/` ([[ros2-mac]]). It loads Unitree's G1 model (`unitree_mujoco/unitree_robots/g1/scene_29dof.xml`, cloned next to the repo; the path comes from `$HARP_G1_SCENE`, set by the pixi environment, or `--scene`) and speaks the robot's low-level topics. It reads `rt/lowcmd` and publishes `rt/lowstate` (unitree_hg) every 5 ms step, with `rpy` and `tick` filled in. It uses DDS domain 1 on loopback; the real robot uses 0. It has an elastic band with keys 7/8/9, and `--auto-release` for scripted tests. There is no `sport` service in any MuJoCo option, so only our own controller ([[gr00t-wbc]]) walks in it.

**Always run it with the viewer** (`ros2 run harp_sim run_sim`, plus `--auto-release` when scripting), never `--headless`, so the teammate can watch the robot move. A teammate asked for this on 2026-10-25. The same goes for rviz2: when testing anything it can show (the lidar, later Nav2), open it in a window and leave it up for the teammate, not just for a screenshot (asked 2026-10-26). Run long-lived windows (sim, rviz2, TF publishers) in Terminal-panel tabs so the teammate can watch and stop them. `screencapture` from Claude's shell only captures the desktop background (no screen-recording permission), so it can't check windows.

**Scripted tests** (how the `--to` results were measured, 2026-10-25; to record such a run now, start `ros2 run harp_ros run_recorder --ros-args -p tag:=...` first, and move_distance logs its moves into the run, [[run-logging]]): start `ros2 run harp_sim run_sim --auto-release 9 --log`, and the controller with `ros2 run harp_control move_distance ...`. Run the controller in a pseudo-terminal (Python `pty.fork`), because `TerminalKeys` reads keys from a real terminal. Pass its flags as separate arguments: one quoted string fails argparse. Press `]` once the logged pelvis z drops below 0.81 (feet down), wait about 6 s, then press `g`, and press `o` after `All moves done`. With `--auto-release` under about 9 s, the band can drop before the stand pose and `]`. If the controller exits, stop the sim, or the band releases a limp robot. For ground truth, take the last `--log` line before each move's `Target` report: the line nearest it can fall inside the next move.

**Why not unitree_mujoco's `simulate_python`** (found 2026-10-25):
- Its bridge computes the PD torque once per received `rt/lowcmd`, on the DDS thread, and holds it. With GR00T this blew up the physics on landing. `run_sim.py` recomputes PD every step from the latest command, like NVIDIA's GR00T sim and the robot's motor drivers.
- Its sleep-based pacing drifts to about 0.8x real time on the Mac (lowstate at 140–170 Hz instead of 200), so a wall-clock 50 Hz policy runs too fast relative to sim time. `run_sim.py` paces against an absolute schedule.
- Running it needs three local fixes. Our scripts need none of them, and we checked they don't import `unitree_sdk2py.utils.thread`. The fixes are: unitree_sdk2_python PR #139 for the Linux-only `timerfd`; `import glfw` in `MujuocoKeyCallback`, because MuJoCo 3.17 dropped `mujoco.glfw`; and editing `config.py`.

**Boxes and lidar** (2026-10-26): `--box X Y [W D H]` adds fixed box geoms to the world body through `MjSpec` (`load_model`), X m ahead and Y m left of the start, default 0.5 m cube. `--lidar` starts `lidar.py`'s `SimLidar`: rclpy (domain 2, no signal handlers) in the same process as the DDS sim (domain 1). Every 0.1 s of sim time the loop hands it a copy of qpos; a thread runs `mj_kinematics` on its own `MjData` and `mj_multiRay` (480 × 40 = 19,200 rays, 360° × −7° to +52° in the lidar frame, 2 cm noise, 5% dropout, 0.1–40 m), skipping only `torso_link` (the head shell). Hits on the rest of the robot stay in the cloud, as on the real robot (a teammate's call, 2026-10-26): self-filtering belongs to the Nav2 pipeline, so it gets tested in the sim. Standing, that's about 640 points per scan, 0.11–0.56 m from the lidar, 0.83–1.17 m above the floor and within 0.37 m of the robot's axis, so inside Nav2's planned height band: without the filter the robot would mark itself as an obstacle. It publishes xyz PointCloud2 on `/utlidar/cloud_livox_mid360`, frame `livox_frame`, in the lidar's own (upside-down) frame. The mount lives in `harp_control/lidar_mount.py` (shared with `walker_node`, so the sim and the transform can't disagree): `mid360_joint` from `g1_29dof.urdf` (0.0002835, 0.00003, 0.40618 on `torso_link`, pitch 0.0401) plus roll π. Our MJCF matches that older URDF (waist offsets 0.035 + 0.019, head at −0.054), not `g1_29dof_rev_1_0.urdf` (0.044 + 0, lidar 0.428434, roll π, pitch 0.0511). For rviz2, `harp_sim/rviz/lidar.rviz` (fixed frame `base_link`). The `base_link` → `livox_frame` transform comes from `walker_node` on `/tf`: the lidar's real pose from the joints and IMU while the policy runs, an upright guess before (z 1.21 m, roll π, pitch 0.0401). So rviz2 needs `walker_node` running ([[nav2-sim]]). Checked: one cast takes about 9 ms on its thread; `/lowstate` stayed at 200 Hz and the lidar at 10 Hz, with no lag warnings in 40 s with or without `--lidar`. On the standing model the nearest floor point is 0.89 m away. With `walker_node` walking about 1 m toward a 1 m tall box at x = 3, the nearest box point went 2.72 → 1.69 m, against 2.73 → 1.70 m from the logged pelvis. Raising one arm forward puts about 2,000 rays on the robot. Standing, the shoulders block the lidar's lowest rays at bearings ±70° to ±101° (about 270 rays each), and the wrists block ±23° to ±40°; these show as body points plus gaps in the floor rings right at each side. Hanging limp from the band before a controller starts, the pelvis is at 1.28 m, not 0.75, so the lidar is about 0.5 m higher than the static TF assumes: rviz2 draws the floor about 0.5 m below the grid and the blind ring is wider (about 1.5 m). Lower the robot with `8` to see it as when standing. In the lidar frame the floor sits near z = +1.25, but the torso lean puts it below +1.15 at about 1.4 m ahead, so height cuts need TF, not raw lidar-frame z.

**ROS 2 and run logging** (2026-10-26): run_sim always starts ROS 2 now (domain 2, no signal handlers), not only with `--lidar`. It publishes the true pose on `/sim/qpos` (`[sim_t, qpos…]`, 20 Hz), a latched `/sim/info` (JSON: scene, world, boxes, the course goal, flags), and events on `/harp/events`: feet_down, band_released (auto or key), band_attached, contact, lag, quit. It ignores the `--ros-args` that launch adds. The short-lived `--record FILE` is gone; run_recorder writes `truth.npz` instead ([[run-logging]]).

**Courses** (2026-10-26; run them with the `course` command, [[run-logging]]): `--world NAME` attaches `harp_sim/worlds/NAME.xml` (or a path) with `MjSpec.attach`, prefixing names with `course/`. Geoms in its worldbody become fixed obstacles; a site `goal` is printed at start-up. Courses are `open_floor`, `one_box`, `slalom` and `obstacle_course`; see [[nav2-sim]]. `ContactReport` prints each new touch between a robot body and any world geom except the floor; touches of the same pair within 1 s count as one, because contacts flicker. Each contact is also an event in the run's `events.csv`. Pass criteria per course (`max_contacts`, time, clearance, ...) are in `worlds/<name>.yaml` ([[run-logging]]).

**Mac facts** (one teammate's Apple Silicon Mac, Python 3.12, 2026-10-25; other OSes untested, see [[team-context]]):
- Loopback is `lo0`, not `lo`. Our scripts pick it automatically.
- The viewer (`launch_passive`) needs `mjpython`, not `python3`. `ros2 run` starts plain python, so `run_sim.py` restarts itself under `mjpython` (from the pip mujoco wheel in the pixi env) unless `--headless`.
- The window throttling shows up as occasional stalls ("the sim fell ~115 ms behind"). Keep the MuJoCo window visible; a stall over 0.5 s stops the controller ("Robot state stopped"), and then both have to be restarted.
- The setup (the pixi environment in `ros2/` plus the Unitree clones) is in the README. `sim-venv` and the source-built CycloneDDS are no longer used (2026-10-25).
- Band keys, per the code: 7 shortens (raises), 8 lengthens (lowers), 9 toggles. Unitree's README has 7 and 8 reversed.

**Alternative, not used:** unitree_rl_gym's `deploy/deploy_mujoco` runs its own 12-leg-joint policy directly in MuJoCo, without DDS.
